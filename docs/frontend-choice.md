# Почему выбран такой фронтенд

Клиент для `/itline` реализован как **статика**: HTML + CSS + нативные ES-модули
(`<script type="module">`, `import`/`export`) + `fetch` к REST API. Без сборщика
(Vite/webpack), без фреймворка (React/Vue), без шаблонизатора (Thymeleaf).

Причина: объём UI мал, требование ТЗ — SPA-поведение через REST, а критерий
приёмки — запуск двумя командами (`docker compose up -d`, `boot:run`). Нативные
модули закрывают задачу без инфраструктуры сборки, которая для такого объёма
непропорциональна.

Если бы UI рос (пагинация, фильтры, журнал, ещё формы) — я бы перешёл на
Vite + Vue/React со сборкой.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Thymeleaf + немного JS** | Всё в одном проекте, знакомо бэкендеру, нет JS-сборки | Смешение шаблонов и SPA-логики; для «без перезагрузки» всё равно нужен JS; сложнее поддерживать при росте | Отклонён: SPA-требование делает шаблонизатор наполовину бесполезным |
| **Статика: HTML + нативные ES-модули + fetch** | Ноль зависимостей и сборки; отладка «как есть»; критерий приёмки выполняется тривиально; нативные модули — фундамент, понятный без магии | Нет tree-shaking/минификации; при росте UI — ручная организация; нет TS/JSX | **Выбран** |
| **SPA-сборка: Vite + Vue/React** | Удобно при сложном UI, HMR, экосистема, TS/JSX | `node_modules`, конфиг, dev/prod-режимы, интеграция с Maven/CI, критерий «две команды» под угрозой | Отклонён: оверкилл для объёма задачи |
| **Статика + Vue через CDN** | Компромисс: реактивность без сборки | Тянет внешний CDN (не офлайн), версия вручную, не «нативные модули» | Возможен, но выбран более простой путь |
